# SPEC: Email me when a service I depend on reports an incident (Statuspage watcher)

Status: ready to build. Audience: self-hosters, freelancers and small teams whose automations depend on third-party services (GitHub, Cloudflare, OpenAI, DigitalOcean, Discord and others) and who want to know it is the vendor's outage before they spend an hour debugging their own workflows.

## Background
Thousands of vendors host their status page on Atlassian Statuspage (and compatible hosts). Each exposes a public JSON API without a key: `https://<host>/api/v2/incidents.json` lists recent incidents with status (`investigating`, `identified`, `monitoring`, `resolved`, plus `scheduled`/`in_progress`/`verifying`/`completed` for maintenance), impact (`none`, `minor`, `major`, `critical`), updates and affected components. Existing n8n templates for "uptime"/"status page" ping your OWN sites or push to a status page, or use Bright Data/GPT (id 18517). None watches vendors' public incident feeds and dedupes by incident and update with only core nodes and an email.

## Problem
Vendor status emails and RSS are noisy, arrive late, or need an account per vendor. One workflow should poll many vendor pages, alert once per incident event (new, updated, resolved) and stay quiet otherwise.

## Scope
Scheduled workflow. For each configured status page: fetch `/api/v2/incidents.json`, detect new incidents, new updates to known incidents and resolutions, filter by minimum impact and optional component keywords, and send one email per page per run summarising the events. Also alert once if a status page cannot be read several runs in a row, and once when it recovers.

## Out of scope
Maintenance windows (ignore `scheduled_maintenances`; only `incidents.json`), status pages not built on Statuspage v2 JSON (say so clearly; do not claim support), Slack/Teams delivery (mention in Customization how to swap the last node), AI summaries, persistence outside workflow static data.

## Nodes and flow (target 11 to 15 nodes plus stickies; core nodes only)
1. `Run every 5 minutes` (Schedule Trigger) and `Run manually` (Manual Trigger).
2. `Set up your status pages and email` (Set node, the ONLY place a user edits values): `pages` (multi-line, one per line, format `Label | https://host`; label optional; example lines for GitHub, Cloudflare, OpenAI pre-filled), `minimumImpact` (`minor` default; one of `none|minor|major|critical`), `componentKeywords` (optional multi-line, case-insensitive; if set, only incidents touching a matching component or whose title matches are alerted), `alertOnResolved` (boolean, default true), `fromEmail` (placeholder `YOUR_SENDER_ADDRESS`), `toEmail` (placeholder `YOUR_RECIPIENT_ADDRESS`), `failuresBeforeAlert` (number, default 3), `ignoreIncidentsOlderThanHours` (number, default 48, applies when an incident is first seen and already resolved), `maxIncidentsPerPage` (number, default 10).
3. `Check settings and list status pages` (Code): validates config, normalises each page URL (adds `https://` if missing, strips path and trailing slash, keeps only origin; http allowed), emits one item per page with `pageKey` (lower-case origin), `label`, `apiUrl`.
4. `Fetch incidents from status page` (HTTP Request GET, JSON, batch size 1 with 1 s interval, 20 s timeout, never error on non-2xx and full response, retry on fail 2 times, normal User-Agent).
5. `Detect new, updated and resolved incidents` (Code, run once for all items): per page, validates the response shape, compares with workflow static data, builds events, applies filters and caps, updates state, tracks consecutive failures, builds the per-page email payload (subject, plain text body, HTML body).
6. `Anything to email?` (If) then `Send incident email` (Send Email node, SMTP, `Email Format` HTML plus text if available, retry on fail 3 times). Credential `smtp` named exactly `SMTP account` (name only, see AC3).
7. Section stickies (white) and one main yellow sticky, per AC2.

## Event rules (for AC6 to AC9)
State per page in `$getWorkflowStaticData('global').pages[pageKey]`: `incidents: { [id]: { status, updatedAt, impact } }`, `failures`, `failureAlerted`, `initialised`.
- New incident id (not in state):
  - not resolved (`status` not `resolved`/`postmortem`/`completed`): event `new`, always (subject to impact/component filters), including on the first run.
  - resolved: no event. Already-resolved incidents seen for the first time are history: store them, never alert. (`ignoreIncidentsOlderThanHours` therefore only limits how much resolved history is stored; keep the setting but document it as a storage limit, or drop the setting if it has no effect and tell me in NOTES.md.)
- Known incident whose `updated_at` or `status` or `impact` changed: if new status is `resolved`: event `resolved` (only when `alertOnResolved`); otherwise event `update`. If nothing changed: nothing.
- Impact filter: an incident passes when its impact rank (none=0, minor=1, major=2, critical=3) is at least `minimumImpact`. A resolution event is sent only for an incident that was previously alerted (`notified: true` in state) and whose stored status was not yet resolved. An incident first seen as resolved history, or one that merely changes `updated_at` while already resolved, never produces a `resolved` event (review finding F2; this replaces the earlier "or passes the filter now" wording, which contradicted AC6).
- Component filter as in step 2.
- Page `initialised` is set after the first successful read. State is pruned to the ids present in the latest response (so state cannot grow forever).
- Failure handling: HTTP status != 200, request error, non-JSON, or JSON without an `incidents` array counts as a failure for that page (one failure per run). When `failures` reaches `failuresBeforeAlert` and not yet alerted: event `unreachable` (once). The next success after an alert: event `recovered` (once). Failures never delete incident state. One broken page never stops the others.
- Per-page email caps at `maxIncidentsPerPage` events, adding a line `+N more events not shown` (state still updated).

## Acceptance criteria
Each criterion needs at least one test whose name starts with the AC id. "Shipped" means the content of `workflow.json`.

- **AC1 Importable structure.** Valid JSON with `name`, `nodes`, `connections`, `settings`. Unique node names and ids, every connection endpoint exists, every non-sticky non-trigger node reachable from a trigger, no disabled or orphan nodes. Every node `type`/`typeVersion` exists in the installed n8n-nodes-base (read `/workspace/n8n-local/node_modules/n8n-nodes-base`; skip with a clear message if absent). Verb-first plain title, at most 80 chars, no emoji. `active` false. No `pinData`, `id`, `versionId`, `meta.instanceId` or other instance-specific fields.
- **AC2 n8n sticky note guidelines** (n8n's "Sticky note guidelines for templates"): exactly one main overview sticky, yellow, top-left (its x and y are the minimum of all nodes and stickies), 100 to 300 words, headings `### How it works` and `### Setup` (optional `### Customization`); Setup names every credential, every config value to edit, how to test, and the static-data limitation. White section stickies (4+ node workflow), each under 50 words with a short heading, each geometrically covering at least two nodes and not the main sticky, covering all functional nodes between them. Red warning stickies only if each covers exactly one node; at most one (on the Send Email node: set sender, recipient and SMTP credential first). No other stickies.
- **AC3 No secrets, credentials by name.** Nothing matching secret patterns (`Bearer `, `api_key`, passwords, SMTP hosts of real providers, personal email addresses, Michal's name). The Send Email node references `smtp` credential type with `name: "SMTP account"` and no real id (omit `id` or whatever n8n import accepts; record the choice in NOTES.md). Email placeholders are obvious placeholders. The HTTP Request node needs no credential.
- **AC4 Config validation.** Code throws a clear message before any HTTP request for: placeholder or empty `fromEmail`/`toEmail` (also reject strings without `@`), no pages, unparsable page line (offending text in message), `minimumImpact` not in the allowed list, non-positive numbers. Accepts `GitHub | https://www.githubstatus.com/`, bare `githubstatus.com`, `https://www.githubstatus.com/api/v2/incidents.json` (reduced to the origin), blank lines and `#` comment lines; de-duplicates by origin.
- **AC5 Node naming.** No default n8n names (`HTTP Request`, `Set`, `Edit Fields`, `Code`, `If`, `Send Email`, `Schedule Trigger`, `Manual Trigger`, with or without numbers). Descriptive, at most 50 characters.
- **AC6 New and resolved logic.** Using the captured fixtures (`fixtures/githubstatus.incidents.json`, `cloudflarestatus.incidents.json`, `openai.incidents.json`, real responses) plus synthetic variations built in tests: first run on a page with only resolved incidents yields zero events but stores state; an unresolved incident on first run yields one `new`; a repeat run yields none; an update (changed `updated_at` or `status`) yields `update`; resolution yields one `resolved` and then none; `alertOnResolved` false suppresses resolved events; resolved events are suppressed for never-notified incidents.
- **AC7 Filters.** `minimumImpact` ranks as specified (unknown or missing impact is treated as `none`); component keywords match affected component names from `incidents[].components[].name` and `incident_updates[].affected_components[].name`, and also the incident name; OpenAI's variant of the payload has no `components` (must not crash).
- **AC8 Failures and recovery.** For HTTP 404 with HTML body (like `status.hetzner.com`), network error items, invalid JSON, and JSON without `incidents`: failure counting, one `unreachable` at the threshold, none after, one `recovered`. State of incidents is kept through failures. Other pages are unaffected. Error items from the HTTP node (when `neverError`/`fullResponse` produce an error object) are handled without throwing.
- **AC9 State hygiene and caps.** State pruned to incident ids present in the latest response; per-page event cap and the `+N more` line; two pages with identical incident ids never collide; running the node twice with the same input produces no repeated events; keys with odd characters (`__proto__`, `constructor`) as page labels or incident ids do not break or pollute (use `Object.create(null)` or `Object.hasOwn`).
- **AC10 Email content.** Subject: `[Status] <Label>: <summary> - <short title of the most severe event>` strictly under 150 chars (at most 149), no newlines, where `<summary>` is, for one event, `new incident`, `update`, `resolved`, `page unreachable` or `page recovered`, and for several events `N events` (review decision: the old `N new event(s)` was wrong for updates and resolutions); body lists each event: event type, incident title, impact, status, affected components (if any), latest update text (cut to 500 chars at a word boundary, including any ellipsis, so never more than 500), start/update time in UTC `YYYY-MM-DD HH:mm UTC`, and incident link (`shortlink` if present, else page origin + `/incidents/<id>`). HTML body escapes all dynamic text (hostile input `<script>`, quotes, `&`). Plain-text body has no HTML. Both bodies under 20000 characters. An update body that is only markup or entities (so empty once flattened to text) renders no update line, not a blank one (clarified in review 2).
- **AC11 Honest limits are documented.** Sticky, README and LISTING state: works only with Atlassian Statuspage v2 JSON pages (list the three fixture vendors as tested at the time of writing); polling interval is not real time; maintenance windows are ignored; state lives in workflow static data so it only persists for active workflows (manual runs do not save it, so a manual test repeats alerts); first run alerts only for incidents that are still open.
- **AC12 Copy quality.** README.md, LISTING.md and sticky text pass `npm run lint:copy` (no em dashes, no banned words, British spelling list as in the other template: organise, colour, licence (noun), behaviour, summarise, analyse, centre, favour).
- **AC13 Property and golden tests.** One seeded randomised test (random sequences of poll responses over several runs against a reference model: the set of events emitted equals the model) and one golden test (fixture sequence in, expected events JSON out in `tests/golden/`).
- **AC14 Live end-to-end (PM-run).** `npm run e2e` (you write `scripts/e2e.mjs`; env `N8N_URL`, `N8N_API_KEY`; starts a local mock Statuspage server and a local SMTP sink) imports `workflow.json` through the public REST API, creates an SMTP credential pointing at the local sink, patches ONLY config values and trigger interval in the imported copy, activates it, then drives the mock through: baseline, new incident, update, resolution, vendor outage (HTTP 500) then recovery, and asserts emails captured by the sink and the execution data. Write it after unit tests pass; without the env vars it exits with a clear message. Do not run it unless `N8N_URL` is set.

- **AC15 Resolution only after a real alert (review F2).** A resolved incident first seen as history, then edited later (new `updated_at`, still resolved, impact passes the filter), emits nothing. An incident that was alerted as open and then resolves still emits one `resolved`.
- **AC16 Out-of-order timestamps (review F3).** A response whose `updated_at` is older than the stored one (and status and impact unchanged) emits nothing and does not move the stored timestamp backwards. A strictly later `updated_at`, or a changed status or impact, still counts as a change. A missing or unparsable `updated_at` is treated the same as an older one: on its own it emits nothing and does not overwrite a known-good stored timestamp (added in review 2).
- **AC17 Subject and text limits (review F4).** Subject length is at most 149 for any title. Update text in the email is at most 500 characters including any ellipsis. Truncation never splits a surrogate pair: no lone half-character is left at the cut (added in review 2).
- **AC18 Sandbox globals.** Code nodes use no `URL`, `Buffer`, `structuredClone` or similar (found live: `URL` is undefined in the n8n Code node). The test sandbox must not provide them. Done in the first fix.
- **AC19 Live end-to-end covers a closed port and an HTML 404 body.** `npm run e2e` includes a page on a closed port and a page that returns HTTP 404 with an HTML body; both count as failures and neither stops the other page.
